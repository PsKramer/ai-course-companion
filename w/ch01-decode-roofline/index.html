One decode step: memory-bound or compute-bound?

Try this

  1. Defaults are Course-8B (Llama-3.1-8B-like, bf16, L = 32, h_kv = 8, d_h = 128 → 131,072 B of KV per token) on one H100 at B = 1, T = 8k. Raise B to 32: aggregate tok/s rises ~11× while per-sequence speed falls ~3×.
  2. Set T = 128 and push B to 512: the step finally turns compute-bound. At T = 512 it never does.
  3. Switch weights to FP8, then try the Llama 3.1 70B preset.

What to notice

At small B each step streams all the weights for only 2·N·B FLOPs, so intensity ≈ B / b_w FLOP/byte, far below the H100 ridge (~295 FLOP/byte in bf16): batching is nearly free throughput. But the KV cache grows with B·T and is not shared across sequences, so intensity saturates at 2·N / (T · KV bytes per token). At long context the KV cache, not the weights, is the bytes you pay for, which is why GQA/MLA, FP8 KV, and paged KV management matter (see 6.2 KV-cache math). FP8 weights halve the bytes but double the ridge.
Model. Decode reads every weight once per step plus each sequence's full KV cache; FLOPs ≈ 2·N·B (matmuls only; attention FLOPs 4·L·T·h·d_h per token are ignored, as are activations and kernel overheads, so real step times are higher). Peak dense FLOP/s: H100 989 T (bf16) / 1979 T (FP8; H100 has no FP4 tensor cores, so FP4 weights use the FP8 rate); B200 2.25 P (bf16) / 4.5 P (FP8) / 9 P (FP4). TP across g GPUs is modeled as ideal g× bandwidth, peak, and capacity (no communication cost).
